// Programa que calcula el promedio de 5 calificaciones de punto flotante

#include <stdio.h>

int main() {

    // Arreglo que almacena 5 calificaciones de tipo float
    float calificaciones[5];
    float suma = 0;
    float promedio;

    // Captura de calificaciones
    // cada numero introducido por el usuario se guarda en un espacio del arreglo calificaciones
    // tambien se va sumando el total de calificaciones para calcular el promedio

    // Calculo del promedio

        printf("  Materia %d: %.2f\n", i + 1, calificaciones[i]);

    printf("\nPromedio: %.2f\n", promedio);

    if (promedio >= 60) {
        printf("Estado: APROBADO\n");
    } else {
        printf("Estado: REPROBADO\n");
    }

    return 0;
}

#Arreglo donde se guardan los datos
datos = []

# PILA

# Agrega al final
def push():
    valor = input("Ingresa un dato para la pila: ")
    datos.append(valor)


# Elimina el ultimo
def pop():
    if len(datos) == 0:
        print("No hay datos")
        return

    # .pop() elimina por defecto el ultimo dato si no se pone un indice
    eliminado = datos.pop()
    print("Dato eliminado:", eliminado)


# COLA

# Agrega al final
def enqueue():
    valor = input("Ingresa un dato para la cola: ")
    datos.append(valor)


# Elimina el primero
def dequeue():
    if len(datos) == 0:
        print("No hay datos")
        return

    # pop elimina el dato en el indice 0 del arreglo
    eliminado = datos.pop(0)
    print("Dato eliminado:", eliminado)


# Muestra la lista
def ver_arreglo():
    if len(datos) == 0:
        print("El arreglo esta vacio")
        return

    print("Arreglo:", datos)

        if lista[i] == objetivo:
            return i
    return -1
print("\nBusqueda secuencial linear")

def busqueda_centinela(lista, objetivo):
    n = len(lista)

    lista.append(objetivo) # agregar centinela

    i = 0
    while lista[i] != objetivo:
        i += 1

    lista.pop() # eliminar centinela

    if i < n:
        return i
    else:
        return -1
print("\nBusqueda centinela: ")
print(busqueda_centinela(arreglo, 8)) # = 3

Pruebas de Escritorio — Análisis de Escenarios

Se analiza el arreglo arreglo = [14, 23, 45, 8, 19] (n=5). Ambos algoritmos (Secuencial y Centinela) tienen complejidad O(n) en el peor caso. La búsqueda con centinela elimina la comparación de límites del ciclo for, reduciendo el número de operaciones por iteración, aunque la complejidad asintótica se mantiene igual.

Mejor Caso — O(1)

Escenario: El elemento buscado se encuentra en la primera posición (índice 0).

arreglo = [14, 23, 45, 8, 19]      objetivo = 14

── Búsqueda Secuencial ──
  i=0: arreglo[0]=14 == 14 ✓      → Encontrado, retorna índice 0
  Comparaciones: 1

── Búsqueda Centinela ──
  Se agrega centinela: [14, 23, 45, 8, 19, 14]
  i=0: arreglo[0]=14 == 14 ✓      → Se detiene
  Se elimina centinela: [14, 23, 45, 8, 19]
  i=0 < n=5 → Encontrado, retorna índice 0
  Comparaciones: 1

Ambos algoritmos terminan en la primera iteración: O(1).

Caso Promedio — O(n/2) = O(n)

Escenario: El elemento buscado se encuentra aproximadamente a la mitad del arreglo.

arreglo = [14, 23, 45, 8, 19]      objetivo = 45

── Búsqueda Secuencial ──
  i=0: arreglo[0]=14 ≠ 45          → continúa
  i=1: arreglo[1]=23 ≠ 45          → continúa

  Comparaciones: 3

  Se agrega centinela: [14, 23, 45, 8, 19, 45]

  Se elimina centinela: [14, 23, 45, 8, 19]
  i=2 < n=5 → Encontrado, retorna índice 2
  Comparaciones: 3 (pero sin verificar i < n en cada paso del while)

En promedio, ambos recorren n/2 elementos. La ventaja del centinela es que ahorra una comparación por iteración (no verifica el límite del arreglo dentro del ciclo).

  i=1: arreglo[1]=23 ≠ 99          → i++

  i=4: arreglo[4]=19 ≠ 99          → i++

# Bubble Sort ----------------------------------------------------
n = len(my_array)

    for j in range(n - i - 1):

            my_array[j], my_array[j + 1] = my_array[j + 1], my_array[j]

# Selection Sort ----------------------------------------------------
n = len(my_array)
for i in range(n - 1):
    min_index = i
    for j in range(i + 1, n):
        if my_array[j] < my_array[min_index]:
            min_index = j
    min_value = my_array.pop(min_index)
    my_array.insert(i, min_value)

# Insertion Sort ----------------------------------------------------
n = len(my_array)
for i in range(1, n):
    insert_index = i
    current_value = my_array.pop(i)
    for j in range(i - 1, -1, -1):
        if my_array[j] > current_value:
            insert_index = j
    my_array.insert(insert_index, current_value)

print("Arreglo ordenado con Insertion Sort:", my_array)


# Merge Sort ----------------------------------------------------
def mergeSort(arr):
    if len(arr) <= 1:
        return arr

    mid = len(arr) // 2
    leftHalf  = arr[:mid]
    rightHalf = arr[mid:]

    sortedLeft  = mergeSort(leftHalf)
    sortedRight = mergeSort(rightHalf)

    return merge(sortedLeft, sortedRight)


def merge(left, right):
    result = []
    i = j = 0

    while i < len(left) and j < len(right):
        if left[i] < right[j]:
            result.append(left[i])
            i += 1
        else:
            result.append(right[j])
            j += 1

    result.extend(left[i:])
    result.extend(right[j:])

    return result


sortedArr = mergeSort(my_array)
print("Ordenado con Merge Sort:", sortedArr)

Bubble Sort:     ~4,950 comparaciones, ~2,400 intercambios   → O(n²)
Selection Sort:  ~4,950 comparaciones, 99 intercambios           → O(n²)
Insertion Sort:  ~2,500 desplazamientos promedio                 → O(n²)
Merge Sort:      7 niveles × ~100 comparaciones por nivel        → O(n log n)

Arreglo original: [842, 12, 934, 10, 563, 712, 45, ...]
Resultado:        [9, 10, 12, 18, 19, 23, 29, 34, ..., 976, 981]

Merge Sort requiere ~700 comparaciones vs ~4,950 de los algoritmos cuadráticos. Factor de mejora: 7x más rápido.

Peor Caso — O(n²)

Escenario: Arreglo ordenado de forma inversa [981, 976, 968, ..., 12, 10, 9]. n=100.

Bubble Sort:     4,950 comparaciones, 4,950 intercambios     → O(n²) MÁXIMO
Selection Sort:  4,950 comparaciones, 99 intercambios            → O(n²)
Insertion Sort:  4,950 desplazamientos (cada elemento va al inicio) → O(n²) MÁXIMO
Merge Sort:      7 niveles × ~100 comparaciones                  → O(n log n) SIN CAMBIO

Merge Sort no se degrada: siempre divide a la mitad independientemente del orden.

Los algoritmos cuadráticos alcanzan su máximo costo. Merge Sort mantiene O(n log n) incluso en el peor escenario, demostrando su superioridad para conjuntos grandes.

Conclusión: Para n=100, la diferencia es notable pero manejable. Para n=100,000, Bubble Sort requiere ~5 mil millones de operaciones vs ~1.7 millones de Merge Sort, haciendo a los algoritmos O(n²) inviables a escala.

import random
import time

datos_ordenados   = list(range(1, 100001))
datos_aleatorios  = random.sample(range(1, 100001), 100000)

REPETICIONES = 10000

def linearSearch(arr, x):
    ops = 0
    for i in range(len(arr)):
        ops += 1
        if arr[i] == x:
            return i, ops
    return -1, ops


def binarySearch(arr, x):
    ops  = 0
    low  = 0
    high = len(arr) - 1

    while low <= high:
        ops += 1
        mid  = low + (high - low) // 2

        if arr[mid] == x:
            return mid, ops
        elif arr[mid] < x:
            low = mid + 1
        else:
            high = mid - 1

    return -1, ops


def interpolationSearch(arr, x):
    ops = 0
    lo  = 0
    hi  = len(arr) - 1

    while lo <= hi and x >= arr[lo] and x <= arr[hi]:
        ops += 1

        if arr[hi] == arr[lo]:
            if arr[lo] == x:
                return lo, ops
            break

        pos = lo + ((x - arr[lo]) * (hi - lo)) // (arr[hi] - arr[lo])

        if arr[pos] == x:
            return pos, ops
        elif arr[pos] < x:
            lo = pos + 1
        else:
            hi = pos - 1

    return -1, ops

def medir(funcion, arr, objetivo):
    idx, ops = -1, 0
    inicio = time.perf_counter()
    for _ in range(REPETICIONES):
        idx, ops = funcion(arr, objetivo)
    fin = time.perf_counter()
    tiempo_promedio = (fin - inicio) / REPETICIONES
    return idx, ops, tiempo_promedio

def ejecutar_prueba(nombre_algoritmo, funcion, objetivo):
    print(f"\n{'─'*54}")
    print(f"  Algoritmo : {nombre_algoritmo}  ({REPETICIONES} repeticiones)")
    print(f"  Buscando  : {objetivo}")
    print(f"{'─'*54}")

    print(f"  [Ordenados]   resultado={resultado:20s}  "
          f"ops={ops:6d}  t_prom={t_prom:.8f} s")

    if nombre_algoritmo == "Secuencial":
        arr_para_buscar = datos_aleatorios
        t_sort = 0.0
    else:
        t0 = time.perf_counter()
        arr_para_buscar = sorted(datos_aleatorios)
        t_sort = time.perf_counter() - t0

    resultado = f"índice {idx}" if idx != -1 else "no encontrado"
    extra = f"  (+ {t_sort:.6f} s de ordenamiento)" if t_sort > 0 else ""

Se comparan tres algoritmos de búsqueda sobre un conjunto de 100,000 datos. La búsqueda secuencial recorre linealmente, la binaria divide el espacio a la mitad, y la interpolada estima la posición del objetivo asumiendo distribución uniforme.

Mejor Caso — O(1)

Escenario: El elemento buscado coincide con la primera posición evaluada por cada algoritmo.

datos_ordenados = [1, 2, 3, ..., 100000]     objetivo = 1 (secuencial) / 50000 (binaria)

── Búsqueda Secuencial (objetivo=1) ──
  i=0: arr[0]=1 == 1 ✓              → 1 operación

── Búsqueda Binaria (objetivo=50000) ──
  mid = (0+99999)//2 = 49999
  arr[49999]=50000 == 50000 ✓        → 1 operación

── Búsqueda Interpolada (objetivo=50000) ──
  pos = 0 + ((50000-1)*(99999-0))//(100000-1) = 49999
  arr[49999]=50000 == 50000 ✓        → 1 operación

Los tres algoritmos encuentran el objetivo en una sola operación en su mejor caso: O(1).

Caso Promedio — O(n) / O(log n) / O(log log n)

Escenario: Objetivo aleatorio (ej: 73542) sobre 100,000 datos ordenados.

── Búsqueda Secuencial (objetivo=73542) ──
  Recorre i=0, 1, 2, ..., 73541
  arr[73541]=73542 == 73542 ✓
  Operaciones: 73,542                → O(n)

── Búsqueda Binaria (objetivo=73542) ──
  Paso 1: mid=49999, 50000<73542    → low=50000
  Paso 2: mid=74999, 75000>73542    → high=74998
  Paso 3: mid=62499, 62500<73542    → low=62500
  ...continúa dividiendo...
  Paso 17: encontrado
  Operaciones: 17                    → O(log n) = O(log₂ 100000) ≈ 17

── Búsqueda Interpolada (objetivo=73542) ──
  Paso 1: pos estimada ≈ 73541      → encontrado casi directo
  Operaciones: 1-3                   → O(log log n) con datos uniformes

Secuencial: 73,542 ops. Binaria: 17 ops. Interpolada: 1-3 ops. La interpolada es ~4,000x más rápida que la secuencial en datos uniformes.

Peor Caso — O(n)

Escenario: Elemento no encontrado (objetivo=0 no existe) o datos con distribución no uniforme.

── Búsqueda Secuencial (objetivo=0) ──
  Recorre los 100,000 elementos completos
  No encontrado → retorna -1
  Operaciones: 100,000               → O(n)

── Búsqueda Binaria (objetivo=0) ──
  Paso 1: mid=49999, 50000>0        → high=49998
  Paso 2: mid=24999, 25000>0        → high=24998
  ...17 divisiones hasta que low > high
  Operaciones: 17                    → O(log n) INCLUSO en peor caso

── Búsqueda Interpolada (datos no uniformes, ej: [1,1,1,...,1,100000]) ──
  La fórmula de estimación falla, degenerando a recorrido lineal
  Operaciones: hasta 100,000         → O(n) en el peor caso

La búsqueda binaria NUNCA supera O(log n). La interpolada puede degradarse a O(n) si la distribución no es uniforme. La secuencial siempre es O(n).

Conclusión: Para 100,000 datos ordenados uniformemente, la búsqueda interpolada es la más eficiente en la práctica. Sin embargo, la binaria es la más confiable porque garantiza O(log n) independientemente de la distribución.

class Materia:
    """Representa una materia dentro del plan de estudios."""

    def __init__(self, nombre):
        self.nombre = nombre
        self.prerrequisitos_de = []
        self.estado = 0  # 0: No visitado, 1: Visitando, 2: Procesado


class GrafoCurricular:
    """Grafo dirigido que modela las dependencias entre materias (prerrequisitos)."""

    def __init__(self):
        self.materias = {}

    def agregar_materia(self, nombre):
        if nombre not in self.materias:
            self.materias[nombre] = Materia(nombre)

    def agregar_prerrequisito(self, materia_base, materia_dependiente):
        self.agregar_materia(materia_base)
        self.agregar_materia(materia_dependiente)
        self.materias[materia_base].prerrequisitos_de.append(materia_dependiente)

    def _dfs_visita(self, nombre_nodo, pila_resultado):
        nodo = self.materias[nombre_nodo]
        nodo.estado = 1

        for vecino in nodo.prerrequisitos_de:
            vecino_nodo = self.materias[vecino]
            
            if vecino_nodo.estado == 1:
                raise ValueError(f"Error: Dependencia circular de materia: '{vecino}'. "
                                 f"El plan de estudios no puede resolverse.")
            
            elif vecino_nodo.estado == 0:
                self._dfs_visita(vecino, pila_resultado)

        nodo.estado = 2
        pila_resultado.append(nombre_nodo)

    def ordenamiento_topologico(self):
        for materia in self.materias.values():
            materia.estado = 0

        pila_resultado = []

        for nombre_materia in self.materias:
            if self.materias[nombre_materia].estado == 0:
                self._dfs_visita(nombre_materia, pila_resultado)

        pila_resultado.reverse()
        return pila_resultado

El Ordenamiento Topológico basado en DFS (Depth-First Search) tiene complejidad O(V + E) donde V es el número de materias (vértices) y E el número de prerrequisitos (aristas). El algoritmo visita cada nodo y cada arista exactamente una vez.

Mejor Caso — O(V + E) con grafo disperso

Escenario: Grafo lineal simple (cadena). V=4 materias, E=3 aristas. Mínima cantidad de aristas.

Grafo: Lógica → HTML/CSS → Frontend(JS) → React

DFS desde "Lógica de Programacion":
  Visitar "Lógica"     → estado=1 (visitando)
    Visitar "HTML/CSS"  → estado=1
      Visitar "Frontend" → estado=1
        Visitar "React"  → estado=1
        React: sin vecinos → estado=2, pila=[React]
      Frontend → estado=2, pila=[React, Frontend]
    HTML/CSS → estado=2, pila=[React, Frontend, HTML/CSS]
  Lógica → estado=2, pila=[React, Frontend, HTML/CSS, Lógica]

Resultado (reversa): Lógica → HTML/CSS → Frontend(JS) → React
Operaciones: V + E = 4 + 3 = 7

Con un grafo disperso (pocas aristas), el algoritmo realiza el mínimo de trabajo posible.

Caso Promedio — O(V + E) con grafo moderado

Escenario: Grafo del programa (Desarrollo Web). V=9 materias, E=11 aristas. Múltiples ramas.

DFS recorre las dos ramas principales:

Rama Frontend: Diseño UI/UX → HTML/CSS → Frontend(JS) → React
Rama Backend:  Lógica → Backend(Node) → BD Relacionales → APIs
Convergencia:  APIs → Cloud, React + APIs → Fullstack

Resultado del ordenamiento topológico:
  1. Diseño UI/UX
  2. Introduccion a HTML/CSS
  3. Logica de Programacion
  4. Programacion Frontend (JS)
  5. Frameworks Frontend (React)
  6. Programacion Backend (Node)
  7. Bases de Datos Relacionales
  8. APIs y Microservicios
  9. Cloud Computing y Despliegue / Desarrollo Fullstack

Operaciones: V + E = 9 + 11 = 20

Cada materia se visita una vez (9) y cada prerrequisito se evalúa una vez (11). Total: 20 operaciones.

Peor Caso — O(V + E) con detección de ciclo

Escenario: Grafo con dependencia circular. El DFS detecta un nodo con estado=1 (visitando) al que se intenta acceder nuevamente.

Grafo con ciclo: A → B → C → A  (dependencia circular)

DFS desde A:
  Visitar A → estado=1 (visitando)
    Visitar B → estado=1
      Visitar C → estado=1
        Vecino de C es A → estado de A = 1 (VISITANDO)
        ¡CICLO DETECTADO!

Salida: "Error: Dependencia circular de materia: 'A'.
         El plan de estudios no puede resolverse."

El ciclo se detecta en O(V + E) sin recorrido adicional.

La detección de ciclos no agrega complejidad adicional: el estado=1 (visitando) actúa como centinela dentro del DFS existente. Complejidad: O(V + E).

Conclusión: El ordenamiento topológico con DFS mantiene O(V + E) en todos los escenarios. Su eficiencia lo hace ideal para resolver dependencias en compiladores, gestores de paquetes y planes de estudio.

Sistema de gestión de citas médicas implementado con un Árbol Binario de Búsqueda (BST), donde cada nodo representa una cita con hora, paciente y motivo. El árbol ordena las citas cronológicamente y detecta conflictos de horario.

# Cita es Nodo del Arbol Binario de Busqueda
class Cita:
    def __init__(self, hora, paciente, motivo):
        self.hora = hora
        self.paciente = paciente
        self.motivo = motivo
        self.left = None
        self.right = None

def insertar_cita(root, nueva_cita):
    if root is None:
        return nueva_cita

    if nueva_cita.hora < root.hora:
        root.left = insertar_cita(root.left, nueva_cita)
    elif nueva_cita.hora > root.hora:
        root.right = insertar_cita(root.right, nueva_cita)
    else:
        print(f"CONFLICTO: Ya existe una cita agendada a las {nueva_cita.hora} para {root.paciente}.")
        
    return root

def mostrar_agenda(root):
    if root:
        mostrar_agenda(root.left)
        print(f"| {root.hora:<7} | {root.paciente:<20} | {root.motivo:<25} |")
        mostrar_agenda(root.right)

La inserción en un BST tiene complejidad O(log n) en un árbol balanceado y O(n) en un árbol degenerado (todas las inserciones hacia un solo lado). El recorrido Inorder siempre es O(n) porque visita todos los nodos.

Mejor Caso — O(log n) por inserción

Escenario: Las citas se insertan en orden que produce un árbol balanceado. Primera cita = 10:00 (raíz central).

Insertar 10:00 (Carlos)    → Raíz
Insertar 08:30 (Ana)       → izquierda de 10:00   (1 comparación)
Insertar 14:00 (Sofia)     → derecha de 10:00     (1 comparación)
Insertar 09:00 (Luis)      → derecha de 08:30     (2 comparaciones)
Insertar 11:30 (Maria)     → izquierda de 14:00   (2 comparaciones)

Árbol resultante (balanceado, altura=2):
              10:00
             /     \
          08:30   14:00
            \     /
          09:00  11:30

Agenda Inorder: 08:30 → 09:00 → 10:00 → 11:30 → 14:00
Comparaciones por inserción: máximo 2 = log₂(5) ≈ 2.3

Con un árbol balanceado, cada inserción requiere a lo mucho log&sub2;(n) comparaciones.

Caso Promedio — O(log n) por inserción + conflicto

Escenario: Inserciones del programa original incluyendo un conflicto de horario (10:00 duplicado).

Insertar 10:00 (Carlos)    → Raíz
Insertar 08:30 (Ana)       → izquierda              (1 comp)
Insertar 14:00 (Sofia)     → derecha                (1 comp)
Insertar 09:00 (Luis)      → 10:00→08:30→derecha    (2 comp)
Insertar 11:30 (Maria)     → 10:00→14:00→izquierda  (2 comp)
Insertar 10:00 (Pedro)     → 10:00 == 10:00
  ¡CONFLICTO! "Ya existe una cita a las 10:00 para Carlos Gomez"
  Detección en O(1) al comparar con la raíz directamente.

Agenda final (Inorder):
| 08:30   | Ana Martinez   | Consulta general  |
| 09:00   | Luis Hernandez | Ortodoncia        |
| 10:00   | Carlos Gomez   | Revision dental   |
| 11:30   | Maria Lopez    | Extraccion        |
| 14:00   | Sofia Ruiz     | Limpieza dental   |

El conflicto se detecta al encontrar una hora duplicada durante la inserción, sin costo adicional.

Peor Caso — O(n) por inserción (árbol degenerado)

Escenario: Las citas se insertan en orden cronológico ascendente, produciendo un árbol degenerado (lista enlazada).

Insertar 08:00 → Raíz
Insertar 09:00 → derecha de 08:00              (1 comp)
Insertar 10:00 → derecha de 09:00              (2 comp)
Insertar 11:00 → derecha de 10:00              (3 comp)
Insertar 12:00 → derecha de 11:00              (4 comp)

Árbol degenerado (altura=4, equivale a lista enlazada):
08:00
  \
  09:00
    \
    10:00
      \
      11:00
        \
        12:00

Comparaciones para insertar el 5º elemento: 4 = n-1 → O(n)
Total comparaciones: 0+1+2+3+4 = 10 = n(n-1)/2 → O(n²) acumulado

El árbol se degenera en una lista enlazada. Para evitarlo se usan árboles autobalanceados como AVL o Rojo-Negro, que garantizan O(log n).

Conclusión: El BST ofrece O(log n) promedio para inserción y búsqueda, pero puede degradarse a O(n) sin balanceo. El recorrido Inorder siempre produce la agenda ordenada cronológicamente en O(n).

Meta 4.3 — Compresión de Huffman

Implementación completa del algoritmo de compresión de Huffman para archivos binarios. Incluye construcción del árbol de Huffman mediante un Min-Heap, generación de códigos de longitud variable, serialización con encabezado JSON, y un sistema de pruebas de rendimiento automatizadas.

huffman.py
import heapq
import json
from collections import Counter

class HuffmanNode:
    def __init__(self, byte_val, freq, left=None, right=None):
        self.byte_val = byte_val
        self.freq = freq
        self.left = left
        self.right = right

    def __lt__(self, other):
        return self.freq < other.freq

class HuffmanCompressor:
    
    @staticmethod
    def _build_tree(freqs):
        heap = [HuffmanNode(byte_val, freq) for byte_val, freq in freqs.items()]
        heapq.heapify(heap)

        if len(heap) == 1:
            node = heapq.heappop(heap)
            parent = HuffmanNode(None, node.freq, left=node)
            heapq.heappush(heap, parent)

        while len(heap) > 1:
            node1 = heapq.heappop(heap)
            node2 = heapq.heappop(heap)
            merged = HuffmanNode(None, node1.freq + node2.freq, left=node1, right=node2)
            heapq.heappush(heap, merged)

        return heap[0] if heap else None

    @staticmethod
    def _generate_codes(root):
        codes = {}
        
        def traverse(node, current_code):
            if node is None:
                return
            if node.byte_val is not None:
                codes[node.byte_val] = current_code
                return
            traverse(node.left, current_code + '0')
            traverse(node.right, current_code + '1')

        traverse(root, "")
        return codes

    def compress(self, input_path, output_path):
        with open(input_path, 'rb') as f:
            data = f.read()

        if not data:
            with open(output_path, 'wb') as f_out:
                f_out.write((0).to_bytes(4, 'big'))
                f_out.write((0).to_bytes(1, 'big'))
            return

        freqs = dict(Counter(data))
        root = self._build_tree(freqs)
        codes = self._generate_codes(root)
        bit_string = "".join(codes[byte] for byte in data)
        padding = (8 - len(bit_string) % 8) % 8
        bit_string += "0" * padding

        byte_arr = bytearray()
        for i in range(0, len(bit_string), 8):
            byte_arr.append(int(bit_string[i:i+8], 2))

        json_freqs = json.dumps({str(k): v for k, v in freqs.items()}).encode('utf-8')
        header_len = len(json_freqs)

        with open(output_path, 'wb') as f_out:
            f_out.write(header_len.to_bytes(4, 'big'))
            f_out.write(json_freqs)
            f_out.write(padding.to_bytes(1, 'big'))
            f_out.write(byte_arr)

    def decompress(self, input_path, output_path):
        with open(input_path, 'rb') as f:
            header_len_bytes = f.read(4)
            if not header_len_bytes:
                with open(output_path, 'wb') as f_out:
                    f_out.write(b"")
                return
            
            header_len = int.from_bytes(header_len_bytes, 'big')
            if header_len == 0:
                with open(output_path, 'wb') as f_out:
                    f_out.write(b"")
                return

            json_freqs = json.loads(f.read(header_len).decode('utf-8'))
            freqs = {int(k): v for k, v in json_freqs.items()}
            padding = int.from_bytes(f.read(1), 'big')
            compressed_data = f.read()

        bit_string = "".join(f"{b:08b}" for b in compressed_data)
        
        if padding > 0:
            bit_string = bit_string[:-padding]

        root = self._build_tree(freqs)
        decoded_bytes = bytearray()
        current_node = root
        for bit in bit_string:
            if bit == '0':
                current_node = current_node.left
            else:
                current_node = current_node.right

            if current_node.left is None and current_node.right is None:
                decoded_bytes.append(current_node.byte_val)
                current_node = root

        with open(output_path, 'wb') as f_out:
            f_out.write(decoded_bytes)

Pruebas de Escritorio — Análisis de Escenarios

El algoritmo de Huffman construye el árbol en O(k log k) donde k = símbolos únicos, y comprime/descomprime en O(m) donde m = tamaño del archivo. La eficiencia de compresión depende de la entropía (distribución de frecuencias) de los datos.

Mejor Caso — Compresión máxima (~75%)

Escenario: Texto altamente redundante. Solo 4 símbolos con frecuencias muy desiguales (A=50000, B=25000, C=12500, D=12500).

Frecuencias: A=50000 (50%), B=25000 (25%), C=12500 (12.5%), D=12500 (12.5%)

Construcción del árbol Huffman:
  1. Fusionar C(12500) + D(12500) = CD(25000)
  2. Fusionar B(25000) + CD(25000) = BCD(50000)
  3. Fusionar A(50000) + BCD(50000) = Raíz(100000)

Códigos generados:
  A = 0        (1 bit)    ← símbolo más frecuente, código más corto
  B = 10       (2 bits)
  C = 110      (3 bits)
  D = 111      (3 bits)

Tamaño original:  100,000 bytes (800,000 bits)
Tamaño comprimido: ~21,875 bytes (175,000 bits)
Ahorro: 78.12%     Integridad SHA-256: PASS

Con alta redundancia, Huffman asigna códigos de 1 bit al símbolo dominante, logrando compresión superior al 75%.

Caso Promedio — Compresión moderada (~40%)

Escenario: Texto literario (fragmento del Quijote repetido). Entropía media con ~60 caracteres únicos.

Frecuencias (muestra): e=4250, a=3800, o=2900, s=2500, ' '=6000, ...

Construcción del árbol: O(k log k) con k ≈ 60 símbolos
Códigos generados (muestra):
  ' ' = 00       (2 bits)   ← espacio es el más frecuente
  'e' = 010      (3 bits)
  'a' = 011      (3 bits)
  'z' = 110110   (6 bits)   ← poco frecuente
  'ñ' = 1101110  (7 bits)   ← muy poco frecuente

Tamaño original:  ~40,000 bytes
Tamaño comprimido: ~24,000 bytes
Ahorro: ~40%       Integridad SHA-256: PASS

El texto natural tiene entropía media. Los caracteres frecuentes (espacio, vocales) obtienen códigos cortos, pero la variedad de símbolos limita la compresión.

Peor Caso — Compresión nula o negativa

Escenario: Datos aleatorios (20 KB de bytes generados con os.urandom). Los 256 valores posibles tienen frecuencia casi uniforme.

Frecuencias: Cada byte (0-255) aparece ~78 veces (distribución uniforme)

Construcción del árbol: O(256 × log 256) = O(256 × 8)
Códigos generados: Todos de ~8 bits (igual que sin comprimir)
  byte_0   = 00000000  (8 bits)
  byte_1   = 00000001  (8 bits)
  byte_255 = 11111111  (8 bits)

Tamaño original:  20,000 bytes
Tamaño comprimido: 20,000 + encabezado JSON ≈ 22,500 bytes
Ahorro: -12.5% (¡NEGATIVO! El archivo crece por el encabezado)
Integridad SHA-256: PASS (la descompresión restaura el original)

Con distribución uniforme, Huffman no puede asignar códigos más cortos que 8 bits. El encabezado JSON agrega overhead, resultando en un archivo más grande que el original.

Conclusión: Huffman es óptimo para datos con alta redundancia (texto, logs). Para datos aleatorios o ya comprimidos, no ofrece beneficio. La complejidad del algoritmo completo es O(m + k log k) donde m=tamaño del archivo y k=símbolos únicos.

import threading
import sys
import heapq
from typing import Dict, Any, List, Tuple, Optional

class TrieNode:
    __slots__ = ('children', 'is_end_of_word', 'frequency', 'value')

    def __init__(self):
        self.children: Dict[str, 'TrieNode'] = {}
        self.is_end_of_word: bool = False
        self.frequency: int = 0
        self.value: Any = None

class Trie:
    __slots__ = ('root', '_lock')

    def __init__(self):
        self.root = TrieNode()
        self._lock = threading.RLock()

    def insert(self, word: str, value: Any = None, frequency: int = 1) -> None:
        if not word:
            return
        word = word.lower()
        with self._lock:
            current = self.root
            for char in word:
                if char not in current.children:
                    current.children[char] = TrieNode()
                current = current.children[char]
            current.is_end_of_word = True
            current.frequency += frequency
            if value is not None:
                current.value = value

    def search(self, word: str) -> Tuple[bool, Optional[Any], int]:
        if not word:
            return False, None, 0
        word = word.lower()
        with self._lock:
            current = self.root
            for char in word:
                if char not in current.children:
                    return False, None, 0
                current = current.children[char]
            if current.is_end_of_word:
                return True, current.value, current.frequency
            return False, None, 0

    def delete(self, word: str) -> bool:
        if not word:
            return False
        word = word.lower()
        with self._lock:
            success, _ = self._delete_helper(self.root, word, 0)
            return success

    def _delete_helper(self, current: TrieNode, word: str, index: int) -> Tuple[bool, bool]:
        if index == len(word):
            if not current.is_end_of_word:
                return False, False
            current.is_end_of_word = False
            current.frequency = 0
            current.value = None
            return True, len(current.children) == 0
        char = word[index]
        if char not in current.children:
            return False, False
        success, should_delete_child = self._delete_helper(current.children[char], word, index + 1)
        if should_delete_child:
            del current.children[char]
            return success, len(current.children) == 0 and not current.is_end_of_word
        return success, False

    def autocomplete(self, prefix: str, limit: int = 5) -> List[Tuple[str, int, Any]]:
        prefix = prefix.lower()
        with self._lock:
            current = self.root
            for char in prefix:
                if char not in current.children:
                    return []
                current = current.children[char]
            heap: List[Tuple[int, str, Any]] = []
            def dfs(node: TrieNode, current_word: str):
                if node.is_end_of_word:
                    item = (node.frequency, current_word, node.value)
                    if len(heap) < limit:
                        heapq.heappush(heap, item)
                    else:
                        if node.frequency > heap[0][0]:
                            heapq.heappushpop(heap, item)
                for char, child_node in node.children.items():
                    dfs(child_node, current_word + char)
            dfs(current, prefix)
            results = []
            while heap:
                freq, word, val = heapq.heappop(heap)
                results.append((word, freq, val))
            return results[::-1]

    def __setitem__(self, key: str, value: Any) -> None:
        self.insert(key, value, frequency=1)

    def __getitem__(self, key: str) -> Any:
        exists, value, _ = self.search(key)
        if not exists:
            raise KeyError(key)
        return value

    def __contains__(self, key: str) -> bool:
        exists, _, _ = self.search(key)
        return exists

    def get(self, key: str, default: Any = None) -> Any:
        exists, value, _ = self.search(key)
        return value if exists else default

    def get_stats(self) -> Dict[str, Any]:
        total_nodes = 0
        total_words = 0
        total_characters_in_words = 0
        with self._lock:
            def traverse(node: TrieNode, depth: int):
                nonlocal total_nodes, total_words, total_characters_in_words
                total_nodes += 1
                if node.is_end_of_word:
                    total_words += 1
                    total_characters_in_words += depth
                for child in node.children.values():
                    traverse(child, depth + 1)
            traverse(self.root, 0)
        trie_mem = self._estimate_trie_memory(self.root)
        list_est_mem = 0
        words_list = []
        with self._lock:
            def collect_words(node: TrieNode, current_word: str):
                if node.is_end_of_word:
                    words_list.append(current_word)
                for char, child in node.children.items():
                    collect_words(child, current_word + char)
            collect_words(self.root, "")
        for w in words_list:
            list_est_mem += sys.getsizeof(w)
        list_est_mem += sys.getsizeof(words_list)
        ahorro_bytes = max(0, list_est_mem - trie_mem)
        porcentaje_ahorro = (ahorro_bytes / list_est_mem * 100) if list_est_mem > 0 else 0
        return {
            "total_nodos": total_nodes,
            "total_palabras": total_words,
            "caracteres_totales_sin_trie": total_characters_in_words,
            "memoria_trie_estimada_bytes": trie_mem,
            "memoria_lista_estimada_bytes": list_est_mem,
            "ahorro_memoria_bytes": ahorro_bytes,
            "porcentaje_ahorro_memoria": round(porcentaje_ahorro, 2)
        }

    def _estimate_trie_memory(self, node: TrieNode) -> int:
        size = sys.getsizeof(node)
        size += sys.getsizeof(node.children)
        for char in node.children.keys():
            size += sys.getsizeof(char)
        for child in node.children.values():
            size += self._estimate_trie_memory(child)
        return size

Las operaciones del Trie (inserción, búsqueda, eliminación) tienen complejidad O(L) donde L = longitud de la palabra, independiente del número total de palabras almacenadas. El autocompletado tiene complejidad O(P + M log k) donde P = longitud del prefijo, M = coincidencias en el subárbol, y k = límite de resultados.

Mejor Caso — O(L) inserción / O(P) autocompletado

Escenario: Inserción de palabra corta y búsqueda con prefijo que tiene pocas coincidencias.

Insertar "dato" (L=4):
  Raíz → 'd' (crear) → 'a' (crear) → 't' (crear) → 'o' (crear, marcar fin)
  Operaciones: 4 (una por carácter) → O(L) = O(4)

Buscar "dato":
  Raíz → 'd' (existe) → 'a' (existe) → 't' (existe) → 'o' (is_end=True)
  Resultado: (True, valor, frecuencia) → O(L) = O(4)

Autocompletar "microdat" (P=8, pocas coincidencias):
  Navegación al prefijo: 8 pasos
  DFS del subárbol: solo 10 palabras coinciden
  Con limit=5 y Min-Heap: O(10 x log 5) = O(16)
  Total: O(8 + 16) = O(24 operaciones)

Con palabras cortas y prefijos específicos, el Trie responde en microsegundos.

Caso Promedio — O(L) / O(P + M log k)

Escenario: Diccionario de 1,100 palabras. Búsqueda del prefijo "transcomput" (resultados del benchmark).

Diccionario: 1,100 palabras generadas combinatoriamente
  10 prefijos x 10 raíces x 10 sufijos = 1,000 compuestas + 100 simples

Autocompletar "transcomput" (P=11):
  Navegación al prefijo: 11 pasos por el camino t-r-a-n-s-c-o-m-p-u-t
  DFS del subárbol: ~10 palabras coinciden
  Min-Heap con limit=5: inserta y expulsa según frecuencia

  Tiempo (1,000 búsquedas):
    Lista: 33.30 ms    (filtrado lineal de 1,100 strings)
    Trie:   7.79 ms    (navegación directa por prefijo)
  Factor: Trie es 4.3x más rápido

El Trie evita recorrer las 1,100 palabras: navega directamente al subárbol del prefijo.

Peor Caso — O(L) inserción / O(P + N) autocompletado

Escenario: Prefijo muy corto que coincide con TODAS las palabras del diccionario.

Autocompletar "" (prefijo vacío, P=0):
  Navegación al prefijo: 0 pasos (empieza en la raíz)
  DFS del subárbol: recorre TODO el Trie (1,100 palabras, 3,655 nodos)
  Min-Heap con limit=5: O(1,100 x log 5)

  Operaciones: O(0 + 3,655) = O(N) donde N = total de nodos

Uso de memoria (peor caso en Python):
  Trie:  951,756 bytes (overhead de objetos Python)
  Lista:  69,116 bytes (strings crudos contiguos)
  
  En Python, el overhead de objetos supera al ahorro de prefijos.
  En C/C++, el Trie ahorra hasta 70% de memoria.

Con prefijos cortos o vacíos, el autocompletado degenera a un recorrido completo del árbol.

Conclusión: El Trie es óptimo para autocompletado con prefijos específicos (O(P + M log k)), superándolo a la lista por un factor de 4.3x. Su fortaleza radica en la navegación determinista por caracteres, independiente del tamaño total del diccionario.

A lo largo de esta asignatura, he consolidado un entendimiento riguroso sobre cómo la selección adecuada de estructuras de datos y algoritmos incide directamente en la eficiencia y escalabilidad de los sistemas de software. La optimización de recursos de la computadora —tanto en tiempo de CPU como en consumo de memoria RAM— no es un lujo académico, sino una necesidad imperativa en el desarrollo de software profesional. Algoritmos con complejidad cuadrática O(n²), como Bubble Sort, resultan funcionales para conjuntos pequeños de datos, pero escalan de manera inaceptable conforme el volumen de información crece. Refactorizar hacia enfoques de complejidad O(n log n), como Merge Sort, o incluso O(log n), como la Búsqueda Binaria, representa la diferencia entre un sistema que responde en milisegundos y uno que colapsa bajo carga real.

El análisis exhaustivo de los tres escenarios posibles —mejor, promedio y peor caso— para cada algoritmo implementado me ha brindado un criterio de ingeniería fundamental: anticipar el comportamiento del software bajo condiciones extremas antes de desplegarlo en producción. Este rigor analítico, combinado con la implementación práctica de estructuras no lineales como Grafos Dirigidos con Ordenamiento Topológico, Árboles Binarios de Búsqueda, algoritmos de compresión como Huffman y estructuras de indexación como el Trie, me ha dotado de las herramientas necesarias para diseñar soluciones que no solo funcionen correctamente, sino que brinden la mejor experiencia de usuario posible con un consumo óptimo de los recursos computacionales disponibles.

En conclusión, la ingeniería de software trasciende la mera escritura de código funcional. Requiere un dominio profundo de la teoría algorítmica, una comprensión clara de las limitaciones del hardware y del lenguaje de programación utilizado, y la capacidad de evaluar trade-offs entre tiempo, espacio y complejidad de implementación.
